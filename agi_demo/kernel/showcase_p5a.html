内核 — 为什么它不是 Transformer

每层携带一个固定大小的矩阵状态 S(快权重 / 线性注意力式联想记忆)。整个会话是一条 token 流,由递归 scan 逐 token 消费:外积写入 S,再以 r=S·q 读回。没有 token 间注意力、没有 softmax over sequence、没有越堆越大的 KV cache。

03

Project 5A — 可覆写记忆:delta vs Hebbian

Project 4 里每个槽只写一次,delta 的"覆盖"优势没被触发(与 Hebbian 打平)。5A 构造同一个槽被反复覆写的任务,查询必须返回最新值。预期:delta 稳住(擦旧写新),Hebbian 退化(S·k ≈ v_旧+v_新 叠加态难解析)。

delta 规则

擦除再写入

S ← γS + β(v−Sk)kᵀ。写键 k 前先减掉它当前的关联 S·k → 覆盖,槽里只留最新值。

Hebbian(消融)

累加叠加

S ← γS + β·v·kᵀ。不擦除 → 同一键多次写入变成 v_旧+v_新+… 的叠加态,旧值可能渗漏。

设计要点: 纯召回(session_hops=0,无算术混淆),session_len=12,扫描 n_slots∈{2,3,4,6,12} → 每槽覆写 12/n_slots 次(1×…6×)。新增 slot_truth_at_ref 标签 = 槽的最新存储值(覆写下正确的监督/探针目标)。
04

结果 — 诚实且有层次的分离

delta 全程完美且零方差;Hebbian 大部分也接近 1.0,唯独最深覆写(6×)掉到 0.910±0.153。分离是真实的,但表现为鲁棒性(方差),而非平均精度的崩塌。

覆写深度扫描(K1 臂,ref_acc,3 seed 均值±标准差)。两条线一路贴着 1.0,直到 6× 覆写:delta 钉在 1.000(误差棒为零),Hebbian 落到 0.910 且误差棒下探到约 0.76。

最深覆写(6×)逐 seed: delta = [1.000, 1.000, 1.000] 不变;Hebbian = [0.998, 0.733, 1.000] —— 一个 seed 崩到 0.733,且其召回随延迟衰减(Δ1:0.77→Δ2:0.69),正是叠加态渗漏的预测信号。
诚实解读: d_state=64、值仅 10 类,v_旧+v_新 的叠加大多仍线性可分,所以 Hebbian 多数时候也能读出最新值。delta 的擦除项彻底消除叠加 → 零方差——它不是"平均更准",而是鲁棒:从不落进坏区间。更强的分离需更小 d_state / 更多值类 / 更深覆写(后续工作)。
因果对照(K0 断读): delta 与 hebb 均为 ref=0.096 ≈ chance(读切断 → 记忆不可用,写规则不影响)。所以 K1/K2 的任何信号都来自"读消费了存储状态",写规则只决定存了什么。

基础设施 — 血泪换来的调度经验

5A 的运行被一场调度器/OOM 事故拖延,最终定位到:这台 notebook 的真正瓶颈是 CPU 内存(~20GB),不是 GPU 显存(183GB)。全流程复盘见 POSTMORTEM_p5a_scheduler.md。

launch_all.py

一次性发射

发完退出,无轮询/重启/kill。仅当整批冷启动 RAM 塞得下时安全——14 任务 × 峰值超 20GB 会被 OOM-killer 清掉。

run_capped.py ✓

按 CPU 内存限流

最多 N 并发,仅当 MemAvailable > 阈值 才启动下一个,错峰。只启动、从不 kill → 不会碰撞。5A 最终用它(max=5)跑成。

dashboard/

数据驱动看板

按 metrics.json 的指标形状自动出图,深色模式 + 可设自动刷新间隔。驱动是按 run-dir 的,换实验要重启。

关键教训: 无 Python traceback + 进程凭空消失 = 外部 kill(OOM-killer),不是代码崩溃。任何调度器在这台机器上都必须先看 MemAvailable,而不只是 nvidia-smi。
